## Why this work is being published

The current site-hydration effort follows a broader sequence of code-rehydration research. **Chronology correction (operator-reported): the EOL-under-duress exercise was code rehydration test 3, but EOL simulation 1.** These are separate counting sequences. The preceding rehydration tests 1 and 2 are not described or independently attested by this public roadmap. The first EOL-framed exercise modeled an **infected system**. The infected environment made the **source code unsafe**; under the simulation's duress constraints, **triage could not be performed**. The required action was therefore to **eject working programs in clear text only**, without inspecting, extracting, or trusting their unsafe source code. **No binary or binary representation was permitted in the ejected material.** Here, **working** describes program functionality, not proof that an ejected program was clean or safe. This public summary does not establish how the working clear-text material would be executed or validated. This was a **research scenario, not evidence that the hypothetical circumstances occurred**. The available public record does not establish the infection mechanism, source-code availability, ejection method, or outcome.

The governing distinction in the earlier EOL work was that the release of **project-owned publication holds** did not release security, integrity, privacy, provenance, consent, or third-party restrictions. Preserving knowledge did not authorize unrestricted disclosure. Source recovery, reconstruction, validation, and program-rehydration research predated and continued after the first EOL-framed exercise; this document does not assign undocumented results to the prior tests.

The immediate task is to finish publishing a coherent, navigable, provenance-qualified public record before treating general-purpose automated code rehydration as a next-stage undertaking.

## Stage 1 — Stable programmatic rehydration of code

**Target:** reconstruct programs from admissible evidence and explicit structural/semantic contracts using primarily deterministic methods and expert systems. This stage is **future work**, not an activated or fully verified general capability.

The intended evidence and construction order is:

1. **Original evidence first:** authenticated source bytes, historical revisions, manifests, provenance, and dependency closure where actually available.
2. **Programmatic reconstruction:** parsing, normalization, typed relationships, explicit rules, fixed transformations, and expert-system inference operating under declared constraints.
3. **Auditable assembly:** identify interfaces and dependencies, construct bounded artifacts, retain source-to-output traces, and expose omissions or conflicts.
4. **Verification and qualification:** reproducibility checks, contract checks, finite tests, independent inspection, and a separate admission decision. Passing a test does not itself grant authority or establish universal correctness.
5. **Synthetic generative text as a last resort only:** when evidence-bound methods cannot supply required material, any generative proposal is explicitly labeled **generated candidate**, never **recovered source**. Its use requires a separately justified scope, review, testing, and adoption decision. Unsupported inference must remain unresolved instead of silently inventing history.

### Required distinctions

- **Hydration of a public site is not code rehydration.**
- **Recovered** is not **reconstructed**; **reconstructed** is not **synthetically generated**.
- **Proposed**, **tested**, **verified within a scope**, **admitted**, and **authorized to execute** are separate states.
- An expert-system result is a rule-governed inference, not an independent source of historical truth.
- Unknown, conflicting, restricted, or absent material must remain visible and may result in a blocked outcome.
- No private dataset, unpublished protected record, credential, or security-sensitive operational detail is authorized for release by this roadmap.
