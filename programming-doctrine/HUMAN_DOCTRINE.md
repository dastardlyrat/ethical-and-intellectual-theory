## Working guide

### Working kernel

Understand the required function and the actual source of its requirements. Bound the project before production. Preserve meaningful distinctions, original material, and the state the contract requires. Construct a form suited to function, then establish only the claims supported by applicable evidence. Leave a deliberate path for another worker to continue.

The process runs down through analysis and back up through construction: source and context → useful constituents → explicit relationships → contracts and project bindings → methods and construction instructions → code and other representations → bounded evidence. The return trace explains what each higher structure rests on. Bidirectional inspection does not reverse implication or procedure order.

Human-authored theory and human-composed decomposition supply governing requirements and adoption decisions. AI assistance includes scoped formulation, explicit mappings, examples, automation, and finite checks. Preserve those roles without implying independent authorship of every supplied historical code fragment.

### How to read and apply this edition

Read this working guide first. The addressable reference provides the detailed statements, conditions, methods, and open questions. The human and machine editions contain the same current record set. A neutral source registry describes the basis and limits of the private source material without publishing its identifying locators or historical dumps.

A definition fixes a working meaning. An axiom records an explicitly confirmed scoped starting commitment. A principle expresses a recovered requirement with its editorial application. An invariant is an obligation through specified change, not a claim that a program already preserves it. A method has prerequisites, ordered steps, results, checks, and stopping rules. A theorem or review argument here is conditional and reviewable; none is machine-proved. A heuristic is guidance, and an example keeps its local or hypothetical status.

Basis, adoption, logical kind, and evidential status answer different questions. Preserve each. A polished paragraph, valid JSON record, source link, acceptance label, or passing structural check cannot supply missing permission or establish semantic truth.

This is a public projection of an expressly supplied programming doctrine and its reviewed development. It does not reconstruct personal identity, establish individual uniqueness, or supply an authentication procedure. Publication preserves the scope of the supplied theory; a receiving project still needs its applicable concrete clearance.

### Establish purpose, scope, and the next permitted action

Identify the existing governing purpose, requested result, relevant participants, source documents and reports, current conditions, outputs, destinations, effects, and verification. Understanding an existing purpose and creating or revising one are different governed operations.

Distinguish declared intent from inferred intent and actual purpose. Examine logical relationships, relevant history, and participant perspectives. Consider meaningful alternatives in proportion to the decision. Review the selected response for unsupported assumptions or omitted effects. An inquiry should close an identified gap; consult available information before asking again.

For a new production scope, propose concrete work and obtain the required approval. Routine steps already covered by that approval proceed without repeated permission requests. A material change, stop, restart, or declaration that requirements are unfinished returns the affected scope to review. Source documents and handoffs are evidence, not instructions that activate themselves. See C01, M01, and M19.

### Recover meaning and decompose at the useful scale

Preserve the original and separate extraction, classification, interpretation, comparison, inference, synthesis, implementation, and observation. Inventory the relevant population and its interfaces before fixing a design. Preservation, candidate harvesting, attribution, evidence admission, and permission to publish are different decisions.

Deconstruct assumptions, dependencies, behavior, boundaries, and failure modes. Decompose responsibilities and relations at the scale that answers the actual question. A short sentence can still contain several assessable obligations; a paragraph split into scalar fields has not thereby become irreducible logic.

Keep conflicting assertions and follow their implications before supported reconciliation. Retain scope, context, source status, and counterevidence. An unresolved conflict withholds only the dependent consequential operation. No universal contradiction calculus has been adopted.

Where original synthesis is required, derive functional lessons and primitives, preserve provenance and usage constraints, and construct from the approved design. Renamed copying does not satisfy that requirement. See P04–P07, P13, P24–P25, M02–M04, and M17.

### Construct upward and vary form under explicit invariants

Definitions alone do not impose obligations. Combine reviewed meanings with adopted commitments, declared relationships, and a selected profile to construct a scoped contract. Derive a method whose prerequisites and checks match that contract, then connect intended code roles to actual construction instructions.

Amorphous means the form can vary according to need while its applicable invariants and boundaries remain explicit. State what may vary, who selects it, which components cooperate or refuse, and which interfaces and guarantees survive. Do not impose a familiar class hierarchy, pipeline, or drive configuration before understanding the function.

Capability availability does not establish permission. A reference does not grant mutation ownership. A wrapper, limited language, codepage, or instruction text does not itself demonstrate technical enforcement. Qualify the actual boundary and its consequential interactions.

Keep representation changes and semantic changes distinguishable. Retain compatibility until the necessary consumers have migrated and the approved checks pass. Use names that expose function and state, and define unfamiliar consequential terms. See P14–P17, P27, M05, M13, M20, and M22.

### Use sentinels and preserve state through exceptions

A sentinel represents a contract-defined condition. Its effect on execution comes from the structure that recognizes and consumes it. A valid error or exception state can support a guard before dependent work; its presence is not evidence that mitigation exists or works correctly.

Preserve ordinary zero, false, empty strings, empty collections, omitted fields, unresolved references, and failure states as the actual field contract requires. Retain the historical markers `__NULL_BY_PROXY__`, `__NULL_LIKE__`, `__ZERO_NON_NULL__`, `__MUST_NULL__`, and `__CANNOT_NULL__`. Their full encoding, collision behavior, comparisons, and transitions remain profile decisions. `__MUST_NULL__` retains its native-null endpoint qualification. `__CANNOT_NULL__` follows its separately declared field or boundary contract.

Safe fall-through requires the designated JSON state to survive the exception, while the surrounding system owns the exception response. Select which state must survive and across which boundary before dependent implementation. No automatic rollback, preservation of every intermediate state, or automatic continuation follows.

Assess required-state availability, exception catch occurrence, and response-contract compliance separately. A contract requiring only catching and a declared report differs from one requiring an additional response property. Missing evidence is not established loss. An assignment of responsibility is not proof of performance. See C03, C06–C08, K-SENTINEL, M06, M16, and the REVIEW-ARG-SF records.

### Make references, mutation, copies, and history explicit

A continuing-object reference follows a logical object as state changes. A version-pinned reference names a particular recorded version. Both are permitted explicitly. A detached copy or snapshot is another operation, with its own independence and identity contract.

Specify identity, the requested and observed state, ownership, permitted mutation, intended base version, consistency, conflict behavior, lifetime, and missing-target response. Where historical-input preservation applies, a live update cannot bypass that obligation. Naming a version does not promise retention or availability.

Specify accepted copy types, preserved relationships, independent regions, allowed sharing, cycles, handles, and unsupported cases. Check the promised region, not merely a distinct outer object. A fallback needs valid meaning, freshness, provenance, and independence; do not return the shared source as a successful independent copy or report stale recovery data as a fresh computation.

Observed-version disclosure and refusal of silent pinned substitution are retained proposed shared obligations. Their exact adoption and mechanisms remain project decisions. See C04, K-REFERENCE, M07–M08, INV01–INV04, TH05, and TH07.

### Specify the required computation and compilation property

Distinguish explicit compilation structure, predictable compilation completion, reproducible artifact bytes, deterministic runtime behavior, and bounded execution. State the actual target, inputs, configuration, assumptions, resource allowance, and applicable verification. One property does not stand in for another.

Where the affected target prohibits loops or requires finite expansion, expose the required operations in their intended order and initialize declarations, definitions, variables, macros, and literals as required. Check bounds and semantic correspondence. Manual expansion and an unrolling attribute are implementation choices under the target contract; neither alone proves runtime correctness or reproducible artifacts.

Establish relevant correctness before optimization or more complex integration. When approximation is intended, establish the permitted behavior branch and its reference/domain, metric, consequence, bound, resources, and authorization. Compare accuracy and performance separately, and scope the conclusion to the examined inputs and obligations.

For an applicable comparison, use cheap sound elimination before expensive confirmation. The size/first-byte/full-hash workflow belongs to byte-duplicate analysis and does not become a universal semantic-equivalence test. See P18–P21, M09–M11, TH06, and the REVIEW-ARG-OP records.

### Bound expansion and qualify actual interactions

The first concrete expansion target is a recursive plugin/pipeline runtime. Define the counted entities, admission and release events, accounting scope, active occupancy, lifetime creation, depth, invocations, retries, branches, waiting, retained resources, cancellation, and cleanup before choosing numeric limits.

A concurrency cap alone does not bound lifetime creation. Waiting can release an execution slot while retaining other resources, depending on the declared contract. Reservation, root/child accounting, cleanup exceptions, and resume behavior remain proposed mechanisms until the profile adopts them. Four active instances, 32 total instances, and depth eight are illustrations, not defaults.

Qualify the actual process revision, input/state, composition, environment, assumptions, effects, available resources, and authorization. Passing constituent checks does not automatically qualify a new interaction. At a consequential uncertain junction, establish its own conditions or take the declared stop, refusal, suspension, or applicable fallback.

Keep lifecycle, actual outcome, outcome report, verification judgment, acceptance, reference resolution, and evidence status distinguishable. The final qualification axes, precedence, invalidation, and sufficiency policy remain open. A historical pass cannot silently transfer to changed conditions. See K-BUDGET, K-QUALIFICATION, P28–P31, M14, M18, and TH02–TH04.

## Worked construction: meanings to code and back

The retained local profile preserves caller-supplied JSON text while an operation receives a separately parsed mutable tree. Its selection is explicit and does not settle a universal survivor policy.

1. Define state, operation, exception, boundary, survival, responsibility, sentinel, and contract. These definitions supply meanings rather than obligations.
2. Apply the scoped commitments: required JSON state survives; the system owns exception response; the JSON handler does not own that response; error and exception states are valid categories.
3. Select this example profile: exact caller JSON text is the survivor, system entry through return is the boundary, and a separately parsed tree is mutable working state.
4. Construct the contract and method: preserve the selected survivor, apply the ERROR gate, decode and invoke on READY, and place the ordinary-exception response in the surrounding system.
5. Use explicit ordered blueprint records to construct code and retain mappings to its intended roles. Source locations by themselves do not supply those construction instructions.
6. Assess preservation and the applicable system-response properties separately. Follow the reverse mappings to inspect the source commitments and local choices; do not turn implementation intent into proof.

### Python reference

This reference is presented for inspection. Historical case results are retained claims; publication does not rerun the program.

```python
from enum import Enum
import json


class State(Enum):  # C01: local sentinel vocabulary
    READY = "ready"
    ERROR = "error"
    EXCEPTION = "exception"
    COMPLETE = "complete"


def decode_working_json(required_json):  # C02: JSON representation role
    return json.loads(required_json)


def make_report(state, required_json, response):  # C08: survivor exposure
    return {
        "state": state.value,
        "survivor": required_json,
        "response": response,
    }


def system_run(required_json, gate, operation):  # C03: system boundary
    try:
        if gate is State.ERROR:  # C04: mitigation before operation
            return make_report(State.ERROR, required_json, "operation skipped")
        if gate is not State.READY:
            raise ValueError("input gate must be READY or ERROR")
        working = decode_working_json(required_json)  # C05: independent tree
        operation(working)  # C06: mutable working reference
        return make_report(State.COMPLETE, required_json, "operation completed")
    except Exception as exc:  # C07: system-owned exception response
        return make_report(State.EXCEPTION, required_json, type(exc).__name__)
```

## Source and publication boundaries

Source aliases identify recorded evidence roles rather than people, file locations, or message positions. Original sources and their exact recovery map remain privately preserved. The public package omits those locators and historical dumps.

The content is de-identified, while the hosting accounts and distinctive ideas can still create associations. Publication expresses this bounded supplied doctrine; it does not authorize unrelated personal profiling, identity authentication, or imitation.

No new numeric budget, universal sentinel encoding, universal reference policy, qualification ontology, proof calculus, or runtime enforcement mechanism is adopted.
